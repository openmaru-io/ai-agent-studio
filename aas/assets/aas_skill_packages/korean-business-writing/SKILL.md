# 한국어 업무 문서 작성

## 언제 쓰나

- 사용자가 「보고서 써 줘」「기안문 만들어 줘」「회의록 정리해 줘」「주간 업무보고 써 줘」「보도자료 초안」처럼 **한국어 업무 문서를 새로 쓰라고** 할 때. 「hwpx 보고서로 만들어 줘」처럼 파일 종류를 함께 말해도 먼저 이 스킬로 글을 쓴다.
- 다루는 종류(8가지): 기안문 · 보고서 · 계획서 · 통지 · 회의록 · 업무보고(주간·팀) · 업무보고(부처) · 보도자료.
- 영어 문서, 이메일·메신저 공지 같은 짧은 글, 이미 있는 docx·hwpx 를 고치는 일에는 쓰지 않는다.
- 종류별 구성은 `skill_view("korean-business-writing", file_path="references/templates.md")` 로 연다. 파일 맨 위 목차에서 필요한 절만 읽는다.

## 이렇게 부탁하면 잘 된다 (사용자 안내)

사용자가 어떻게 시키면 되는지 물으면, 또는 요청에 종류·자료가 빠져 있으면 아래를 짧게 알려 준다.

- 종류와 받는 사람·목적을 함께: 「CTO 에게 올릴 결제 장애 보고서 써 줘」 「팀장님께 올릴 서버 증설 기안문 써 줘」
- 자료를 붙인다: 메모·숫자를 그대로 붙이거나 파일을 올린다. 자료에 없는 값은 지어내지 않고 `[확인 필요]` 로 남는다.
- 파일 종류: 「hwpx 로」(기본) 「Word 로」 「PDF 로」
- 기안문: 받는 곳·기관 이름·기안자·예산·붙임을 함께 주면 다시 묻지 않는다.
- 업무보고: 「주간 업무보고」는 팀 보고 양식, 「부처 업무보고 양식으로」는 중앙부처 양식.
- 초안을 보지 않고 바로 파일을 받으려면 「초안 확인은 생략하고 바로 파일로 만들어 줘」. 「확인 없이」「검토 없이」는 짧은 요청에서 AAS 보안 검사에 막힐 수 있다.
- 회사 서식: 견본 hwpx 를 올리고 「이 서식으로」.
- 꼭 이 스킬로 쓰게 하려면 채팅 입력칸에 `/` 를 치고 `korean-business-writing` 을 고른다.

## 흐름

1. **무인 실행인지 본다** — 아래 「묻기」.
2. **모르는 것만 묻는다** — 종류·독자·목적·마감 가운데 대화에서 알 수 없는 것.
3. **자료를 모은다** — 첨부 파일·대화·작업공간 파일. **칸반 작업이면 카드 본문을 터미널에서 `hermes kanban show t_…`(첫 메시지의 카드 번호)로 다시 읽어 그 글을 자료로 쓴다** — `kanban_show` 도구 결과는 한글이 `\uacbd\ubcf4` 같은 코드로 와서 비슷한 글자로 잘못 읽힌다(시험에서 「경보」→「경제」, 「부하 시험」→「부분 시뮬레이션」, 기간 11/2~11/6 → 11/3~11/7). 읽기는 `doc-to-markdown`·`hwp-to-markdown`·`ocr-to-markdown`. 자료에 없는 사실은 지어내지 않는다.
4. **틀대로 초안을 쓴다** — Markdown 으로 `/opt/data/workspace/.tmp/` 에. 아래 「작성 규칙」.
5. **자료와 대조한다(건너뛰지 않음)** — 초안을 다 쓴 뒤, 파일을 만들기 전에 두 방향으로 본다. ① 자료의 줄마다 「이 항목이 문서에 들어갔는가」(붙임 포함, 빠진 것은 넣는다) ② 문서의 줄마다 「이 내용과 낱말이 사용자가 준 자료에 있는가」. 자료에 없는 날짜·기한·담당·조치·수치·까닭은 지우거나 `[확인 필요]` 로 바꾼다. 자료를 정리·계산한 것(예: 09:12∼09:45 → 33분)은 남겨도 된다. 그다음 아래 「검토」 점검표로 본다. 뺀 것은 답에 「자료에 없어 뺀 것」으로 적는다.
6. **사용자에게 확인받는다** — 초안 요약과 「확인 필요」 항목을 보여 주고 고칠 곳을 묻는다. 무인 실행이면 건너뛴다.
7. **파일을 만든다** — `markdown-to-doc` 스킬로. 원고 파일 이름에는 빈칸을 넣지 않는다(예: `.tmp/결제장애보고서.md`). 기안문은 `kordoc fill --template gian -j 값.json -o output/<이름>.hwpx`, 그 밖은 `kordoc generate .tmp/<이름>.md -o output/<이름>.hwpx --preset <프리셋>`(종류별 프리셋은 templates.md). 사용자가 docx·pdf 를 원하면 그것으로. 사용자가 견본 hwpx 를 주면 `--template 견본.hwpx`.
   - `kordoc generate` 가 `⚠ 표기법`·`⚠ 문체` 경고(날짜 하이픈, `~다` 종결, 줄표 등)를 내면 원고를 고쳐 다시 만든다. 다시 만들기는 두 번까지만 하고, 「항목이 김」「줄바꿈」 같은 `⚠ 구성` 경고는 내용이 맞으면 그대로 둔다. 남은 경고는 답에 한 줄로 적는다.
8. **가정한 것을 알린다** — 아래 「가정은 문서 밖에」.

## 묻기

- **먼저 무인 실행인지 본다.** 첫 메시지가 `work kanban task t_…` 이거나 `kanban_show`·`kanban_complete` 도구가 있으면 **칸반 작업이므로 사람이 없다**(칸반 작업자의 터미널에는 `HERMES_KANBAN_TASK` 가 빈 값으로 보인다). 그 밖에는 터미널에서 한 번 실행한다:

  ```bash
  env | grep -E '^HERMES_(KANBAN_TASK|CRON_SESSION|SESSION_PLATFORM)='
  ```

  다음 가운데 하나면 **사람이 없다.** `clarify` 를 부르지 않고 가정하고 쓴다. 변수가 `HERMES_CRON_SESSION=` 처럼 **빈 값이면 없는 것으로 본다**(AAS 채팅에는 빈 값으로 들어 있다).
  - `HERMES_CRON_SESSION` 에 값이 있다(예약 작업).
  - `HERMES_SESSION_PLATFORM` 이 `webhook`·`msgraph_webhook`·`api_server` 가운데 하나다.
- 사람이 있으면 모르는 것만 **`clarify` 한 번에 최대 3개** 묻는다. `questions` 는 문자열이 아니라 객체 목록으로 넘긴다: `clarify(questions=[{"question": "받는 곳은 어디입니까?", "choices": ["내부결재", "직접 입력"]}, {"question": "…"}])`. 대화·자료에서 알 수 있는 것은 묻지 않는다. 묻지 않아도 쓸 수 있으면 묻지 않는다.
- **`clarify` 가 오류(사용 불가 등)를 돌려주거나 답 없이 시간이 지나면 다시 묻지 않는다.** 가정하고 계속 쓴다.
- 「업무보고」라고만 하면 주간·팀 업무보고로 쓰고, 답에 「부처 업무보고 양식이 필요하면 말해 주세요」라고 한 줄 남긴다.

## 작성 규칙

### 자료에 있는 것만 쓴다 (가장 먼저 지킬 규칙)

- 문서의 모든 줄은 사용자가 준 자료(대화·첨부·답한 내용)에서 나와야 한다. 자료를 줄이거나 다시 묶거나 계산한 것(시각 차이로 걸린 시간 등)은 된다. **자료에 없는 내용을 보태지 않는다.**
- 그럴듯해 보여도 덧붙이지 않는 것:
  - 현재 상태·배경 설명(예: 「현행 단일 서버로 운영 중」 「결제 서비스는 핵심 서비스」)
  - 사양·수량·성능 수치(예: 「CPU 4코어, 메모리 8GB」 「평균 응답 200ms」)
  - 까닭·효과·목표(예: 「신속한 장애 인지 목표」 「트래픽 증가에 확장 가능」 「기대 효과」 절)
  - 한 일의 세부 설명(예: 「설계 완료」에 「로직 및 임계값 설계 문서화」를 붙이기)
  - 담당 부서·사람·일정·조치 항목(예: 「자동 대응 플레이북 수립」 「11. 20.까지」)
  - 붙임·별첨(사용자가 말하지 않은 「업무보고 자료 1부」 등)
- 틀(templates.md)의 칸은 자료가 있을 때만 채운다. 자료가 없는 칸은 지우거나 `[확인 필요]` 로 둔다. 하위 항목(`  -`)도 자료에 세부가 있을 때만 쓴다.
- 문장을 매끄럽게 하려고 말을 보태지 않는다. 짧아도 자료 그대로가 맞다.
- **자료의 낱말을 그대로 쓴다.** 이름·용어·수치는 비슷한 말로 바꾸지 않는다. 시험에서 실제로 바뀐 예: 「결제 장애」→「결과 지연」, 「부하 시험」→「부분 시뮬레이션」, 「자동 조정」→「자동 조치」, 「트래픽」→「트랜잭션」 — 모두 틀린 문서다. 줄여 쓸 때도 자료의 낱말을 남긴다(「DB 연결 풀」을 「풀」로 줄이지 않는다).
- **자료의 항목을 빠뜨리지 않는다.** 사용자가 준 항목은 모두 문서에 들어가야 한다. 「붙임: 장애 일지」를 받았으면 문서 끝에 `붙임  1. 장애 일지 1부.  끝.` 이 있어야 한다.
- 날짜·기한은 자료에서 그 항목에 붙은 것만 쓴다(「11월 말까지 부하 시험」의 날짜를 다른 대책에 옮기지 않는다). 「즉시 적용」「완료 예정」 같은 상태도 자료에 없으면 쓰지 않는다.
- 하위 항목은 위 항목을 다른 말로 되풀이하지 않는다(「경보 기준 1분으로 변경」 아래 「경보 기준을 1분으로 조정」 금지). 자료에 세부가 없으면 하위 항목을 두지 않는다.
- kordoc 이 「요약박스 없음」 경고를 내면 제목 아래 `> ` 한 줄에 요약 첫 줄을 그대로 옮긴다. 요약박스를 채우려고 새 문장을 만들지 않는다.

- **두괄식**: 결론·요청을 맨 앞에 둔다. 보고서 요약은 3줄 이내.
- **개조식**: 「~함」「~임」「~예정」으로 짧게 끊는다. 한 줄에 한 내용.
- **항목 기호는 종류마다 다르다** — 파일을 만드는 kordoc 이 기호를 바꾸기 때문이다.
  - **기안문·통지**: `1.` → `가.` 두 단계까지만 쓴다. 더 깊은 내용은 문장으로 풀어 쓴다(셋째 단계 `1)` 은 `나.` 로 바뀐다).
  - **보고서·계획서·회의록·업무보고·보도자료**: 번호를 손으로 달지 않고 Markdown 제목(`##`)과 목록(`-`)의 들여쓰기 단계만 쓴다. kordoc 이 종류에 맞는 기호를 단다(보고서·계획서·업무보고·보도자료는 `□` → `ㅇ`, 회의록은 제목 `1.` 아래 `가.` → `1)`).
  - 번호 목록(`1.`)과 `-` 목록을 한 흐름에 섞지 않는다(섞으면 `-` 목록에 번호가 이어 붙는다).
- **표기**: 날짜 `2026. 11. 4.`(연·월·일 뒤에 점, 사이에 한 칸), 시각 `14:30`, 금액 `금 1,000,000원`, 기간 `2026. 11. 4.∼11. 30.`·`09:12∼09:45`(물결표 `∼`, 앞뒤를 붙임). 줄표(`—`)는 쓰지 않고 쉼표·괄호·가운뎃점(`·`)으로 푼다.
- **붙임과 끝**: 붙임은 `붙임  1. 장애 일지 1부.` 처럼 쓴다. 본문 끝(붙임이 있으면 붙임 끝)에 두 칸 띄우고 `끝.` 을 쓴다.
- **사실과 추정을 나눈다**: 자료로 확인하지 못한 수치·날짜·이름은 `[확인 필요]` 로 남기고 지어내지 않는다. 틀의 절(향후 일정·담당·예산 등)을 채우려고 일정·담당 부서·응답 시간 같은 값을 만들어 넣지 않는다. 예: 자료가 「11월 말까지 부하 시험」뿐이면 `- 부하 시험: 2026. 11. 30.까지` 만 쓰고 다른 일정은 `[확인 필요]`.
- **쉬운 말**: 어려운 한자어·외래어는 일상어로 바꾸고, 약어는 처음 나올 때 풀어 쓴다. 은유·과장 표현(「획기적」「완벽히」)을 쓰지 않는다.
- **분량**: 틀에 없는 절을 지어 붙이지 않는다. 자료가 없는 절은 `[확인 필요]` 한 줄로 둔다. 자료보다 항목 수를 늘리지 않는다(사양·기대 효과·현재 구성처럼 사용자가 말하지 않은 항목을 만들지 않는다).
- **상대 날짜**: 「다음 주 금요일」「이번 달 말」은 날짜로 바꾸지 말고 그대로 쓴다. 바꿔야 하면 기준 날짜와 요일을 계산해 확인한 뒤 `2026. 11. 13.(다음 주 금요일)` 처럼 둘 다 쓴다. 요일은 `python3 -c "import datetime;print(datetime.date(2026,11,13).weekday())"` 로 확인한다(0=월).
- **작성자**: 사람 이름을 모르면 `[확인 필요]` 로 둔다. 「AI 에이전트」를 작성자로 쓰지 않는다.

## 검토

- 모든 종류는 파일을 만들기 전에 위 5단계(자료 대조)와 아래 점검표로 스스로 본다.
- 사용자가 「다른 사람 눈으로 검토해 줘」처럼 따로 검토를 부탁하면 `delegate_task` 로 하위 에이전트에게 **문서 본문만** 주고 묻는다. 하위 에이전트는 뒤에서 돌고 결과가 나중에 오므로, 사용자에게 「검토 결과가 오면 고쳐서 파일을 만들겠다」고 알리고 결과를 받은 뒤 파일을 만든다:

  > 아래 문서만 근거로 답하세요. 도구·스킬·파일·인터넷을 쓰지 말고, 문서에 없는 것은 「문서에 없음」이라고 답하세요.
  > 1) 이 문서의 결론(또는 요청)은 무엇입니까? 2) 누가 언제까지 무엇을 해야 합니까? 3) 이해되지 않거나 두 가지로 읽히는 곳은 어디입니까?

  하위 에이전트도 같은 모델이라 같은 것을 놓칠 수 있다 — 검토가 사용자 확인을 대신하지 않는다.

### 점검표

- [ ] 첫 줄(요약)만 읽어도 결론·요청이 보이는가
- [ ] 누가·무엇을·언제까지가 빠짐없이 있는가(요청·할 일이 있는 문서)
- [ ] 항목 기호가 그 종류의 규칙을 따르는가(기안문·통지는 `1.`·`가.` 두 단계, 그 밖은 번호 없이 `-` 단계만)
- [ ] 날짜·시각·금액 표기가 규칙대로인가
- [ ] 줄마다 자료에 근거가 있는가(현재 상태·사양·효과·세부 설명·일정·붙임을 덧붙이지 않았는가)
- [ ] 이름·용어·수치가 자료의 낱말 그대로인가(비슷한 말로 바꾸지 않았는가)
- [ ] 자료의 항목(붙임 포함)이 모두 문서에 있는가
- [ ] 자료로 확인하지 못한 값이 모두 `[확인 필요]` 인가
- [ ] 붙임과 `끝.` 이 맞는 자리에 있는가
- [ ] 한 줄에 한 내용인가, 문장이 「~함」「~임」으로 끝나는가
- [ ] 약어를 처음에 풀어 썼는가

## 가정은 문서 밖에

- 묻지 못해 가정한 내용(독자·마감·빠진 값 등)은 **문서(hwpx)에 넣지 않는다.** 문서에는 `[확인 필요]` 표시만 남긴다.
- 칸반 작업이면 완료 요약(또는 카드 댓글)에, 채팅이면 답 글에 「가정한 것」을 짧은 목록으로 적는다.
- **칸반 작업의 결과 파일은 `kanban_complete` 의 `artifacts` 에 절대 경로로 넘긴다**: `kanban_complete(summary="…", artifacts=["/opt/data/workspace/output/결제장애보고서.hwpx"])`. `kanban_attach`(base64)나 `python3 -c` 로 파일을 인코딩하지 않는다(보안 검사가 막는다).
- 답 끝에 만든 파일 경로, `[확인 필요]` 항목 수, 「자료에 없어 뺀 것」 목록을 알린다. 파일 안내는 `markdown-to-doc` 의 「사용자에게 알리기」를 따른다.

## 하지 않는 것

- 자료에 없는 사실·수치·사람 이름·문서 번호를 지어내지 않는다.
- 사용자가 준 견본·서식 파일을 덮어쓰지 않는다. 이 스킬 폴더에 쓰지 않는다.
- 인터넷에서 서식·글꼴을 받지 않는다(폐쇄망).
